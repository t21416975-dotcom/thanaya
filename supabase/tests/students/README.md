# اختبارات نظام الطالب وتسجيل الدخول و"امتحان الأخطاء"

اختبارات SQL حقيقية تعمل على PostgreSQL فعلي (17.5) — لا محاكاة، لا mocking.

## التشغيل

```bash
./run.sh "postgresql://postgres:postgres@127.0.0.1:5432/postgres"
# أو
DATABASE_URL="postgresql://..." ./run.sh
```

> ⚠️ **تحذير**: السكربت يحذف قاعدة `thanaya_students_test` ويعيد بناءها.
> لا تشغّله أبدًا على قاعدة إنتاج.
>
> **يجب أن يكون الخادم يدعم UTF-8.** نستخدم `C.UTF-8` عند إنشاء القاعدة لأن
> تطبيع النص العربي يعتمد على character classes مثل `[[:alnum:]]` التي لا تعمل
> في قواعد `SQL_ASCII` (القيمة الافتراضية عند `LC_CTYPE=C`).

## ماذا يفعل السكربت

1. ينشئ قاعدة نظيفة بترميز UTF-8
2. يحاكي بيئة Supabase: أدوار `anon` / `authenticated` / `service_role`،
   ومخطط `auth` فيه `auth.uid()` و `auth.users` و `auth.identities` (لمزوّد Google)
3. يشغّل كل `supabase/migrations/*.sql` بالترتيب
4. يثبّت بيانات الاختبار (3 طلبة + 3 أعضاء طاقم + مادتان + 4 امتحانات + 13 سؤالًا)
5. يشغّل السيناريوهات 02 → 10، **أي فشل يوقفه**

## أهم ما تحرسه الاختبارات

### منع الغش وتسريب الإجابات
- `B2` / `J3`: حمولة `start_exam_attempt` **لا تحتوي** `correct_index` ولا
  `correct_option_index` ولا `explanation` — لا تسريب لمفتاح الإجابة.
- `B5`: `attempt_answers.is_correct` يبقى `NULL` حتى التسليم — لا تصحيح تدريجي
  يكشف النتيجة.
- `C10a/b`: توكن مزيّف أو فارغ → مرفوض.
- `J2b/c`: توكن محاولة أخرى، أو تعديل حرف واحد فيه → مرفوض.
- `J3b`: `get_attempt_questions` قبل التسليم لا تُعيد مفتاح الإجابة.

### التحكم في الصلاحيات
- `A5`: **صفر** صلاحيات كتابة (`INSERT/UPDATE/DELETE`) لـ `authenticated` على كل
  جداول الطالب — نتحقق من `information_schema.role_table_grants` لا من RLS وحدها.
  (اكتشاف مهم: Supabase يمنح `authenticated` كل الصلاحيات افتراضيًا، فكان
  `GRANT SELECT` وحده لا يكفي.)
- `A2`–`A4` / `H1`–`H6`: لا يمكن للطالب التلاعب بالنتائج أو استدعاء دوال إدارية.
- `G2a`–`G2c`: أدمن عادي لا يرى بيانات الطلبة (المفاتيح خارج قوالب الأدمن).
- `G2d`: أدمن عادي **يستطيع** `get_question_analytics` — لأنه تجميعي لا شخصي.
- `G4`: حساب معطّل (`is_active=false`) لا يرى شيئًا رغم منحه الصلاحيات.
- `K4a`–`K4g` / `K5a`–`K5d`: `anon` محجوب تمامًا + لا جدول بلا RLS + أسرار
  `private.app_secrets` غير مقروءة لأي دور عميل.

### "امتحان الأخطاء"
- `D3`: **كل** الأسئلة التي أخطأ فيها الطالب مُدرجة في الامتحان الجديد.
- `D4`: لا تكرار، ولا أسئلة من مادة أخرى.
- `E1`→`E4`: تدرّج الإتقان — إجابة صحيحة واحدة لا تكفي، إجابتان تُخرج السؤال
  من مرشحي "امتحان الأخطاء".
- `E4b`: لا تقنن زائفة — الإتقان يحتاج إجابتين صحيحتين فعلاً.
- `D8`: التحقق من `p_count` (الحد الأدنى والأقصى).
- `J1`: حد المعدّل (30 محاولة أخطاء/ساعة) يُطبَّق فعلاً.

### سلامة البيانات
- `I1`: حذف الطالب ينظّف `exam_attempts` + `attempt_answers` +
  `question_performance` + `student_subject_stats` (cascade).
- `I3c`: `admin_delete_attempt` **يعيد حساب** `question_performance` —
  لا تبقى أرقام متقنة بعد حذف محاولتها.
- `J5`: `save_answer` يرفض سؤالًا لا ينتمي للمحاولة.

## ملاحظات

### لماذا أعمدة `question_performance` بصيغة `times_correct + times_wrong <= times_seen`
السؤال الذي يُترك بلا إجابة يُحسب "ظهورًا" لا "خطأً" (`is_correct IS NULL`).
الطالب لم يخطئ — لم يجب أصلًا. ولا يغذّي "امتحان الأخطاء" لأن المرشحين
مُفلترون بـ `times_wrong > 0`.

### لماذا `sha256` وليس `hmac`
`hmac()` من إضافة `pgcrypto`، وعلى Supabase يقع في مخطط `extensions` ويحتاج
qualification. استخدمنا `sha256()` المدمج في PG11+ مع تغليف السر على الجانبين
`H(secret || payload || secret)` — آمن ضد length-extension وبدون أي امتداد.

### لماذا تجزئة واحدة للمحاولة كلها
`exam_attempts.answer_token` = تجزئة **كل** أسئلة المحاولة مع مفاتيحها.
لو وزّعنا هاش لكل سؤال على حدة، كانت 4 محاولات لكل هاش كافية لكشف كل الإجابات.
